3. PORTFOLIO / TRADING RULES
======================================================================

Validation and Official each start with USD 1,000,000 cash in independent accounts.
Long-only.
No leverage.
No short selling.
Fractional shares allowed.
Every decision contains all 30 symbols, including zeros.
Each stock target weight must be a finite JSON number between 0 and 0.30 inclusive.
Total stock weight must be <= 1. Any remainder stays in cash.
Weights are target portfolio weights, not trade quantities.
The backend derives buys/sells from current holdings and execution prices.
Transaction fee: 0.1% of total buy-plus-sell notional on each rebalance, including initial allocation.
Holdings carry between rounds and overnight.
Missing/invalid selected decisions generally mean no rebalance and existing holdings continue.
A valid all-zero target liquidates equities to cash.
The earliest attributable in-window attempt can consume the slot even if invalid; a later upload cannot simply correct it. This makes pre-submit validation critical.

4. EVALUATION — THIS SHOULD DRIVE STRATEGY DESIGN
======================================================================

Official ranking uses four metrics:
M1 Cumulative Return — higher is better.
M2 Sharpe Ratio — higher is better.
M3 Maximum Drawdown — lower is better.
M4 Turnover — lower is better.

Teams receive a rank on each metric.
Overall Rank Score = mean of the four metric ranks.
Lower Overall Rank Score is better.
Tie-break order: higher cumulative return, higher Sharpe, lower maximum drawdown, lower turnover.

Implication:
Do NOT optimize only raw P&L. A strategy that generates excellent return by taking unstable concentrated positions or constantly rebalancing may lose on Sharpe, drawdown and turnover. The portfolio constructor should explicitly trade off expected alpha versus risk and trading cost.

Sharpe is computed on decision-period returns, annualized using sqrt(252*7)=42.
Turnover averages buy-plus-sell notional divided by pre-round NAV.
Maximum drawdown also observes official daily closes in addition to completed period endpoints.

7. TARGET SYSTEM ARCHITECTURE
======================================================================

Do not start with a monolithic "AI trader." Build layers:

A. DATA LAYER
- Pull permitted public price/volume data and optional public news/filings.
- Normalize timestamps/time zones.
- Cache raw snapshots with retrieval time.
- Validate freshness/missingness.
- Never use post-deadline information for a decision.

B. FEATURE LAYER
Candidate groups:
- Cross-sectional momentum at several horizons.
- Intraday short-horizon reversal.
- Realized volatility/range.
- Relative volume/liquidity.
- Gap/open-to-current behavior.
- Market and sector breadth.
- Beta/market sensitivity.
- Dispersion/correlation regime.
- Optional public-news/filing sentiment/event features.

C. ALPHA/MODEL LAYER
Start with transparent baselines:
1) equal-weight / cash baseline;
2) momentum rank;
3) short-horizon reversal rank;
4) volatility-scaled relative strength;
5) sector-relative signals.

Then test combinations:
- regularized linear model;
- tree-based model;
- regime-dependent ensemble;
- optional LLM-produced event/news score.

Avoid deep RL/neural networks merely for sophistication. With only 30 assets, seven intraday decision points and a short official horizon, robust signal engineering + portfolio/risk design may outperform a brittle high-capacity model.

D. PORTFOLIO CONSTRUCTION
Input: expected relative attractiveness + risk estimates + current holdings.
Output: 30 target weights.
Constraints:
- 0 <= w_i <= 0.30
- sum(w_i) <= 1
- cash allowed
- long-only
Objectives should account for:
- expected alpha
- volatility/covariance
- concentration
- drawdown risk
- estimated turnover
- 0.1% trading fee
Use a no-trade threshold/hysteresis so small signal changes do not trigger fees.

E. SAFETY / EXECUTION
Before every candidate live decision:
- verify correct phase and round;
- verify timestamp and data cut-off;
- include exactly all 30 tickers;
- confirm numeric finite weights;
- confirm each <= 0.30;
- confirm sum <= 1;
- compare against current holdings and turnover;
- log data snapshot hash/version, strategy version and proposed weights;
- perform dry-run validation;
- upload once only when valid;
- save receipt/checkpoint.

8. EXPERIMENTAL METHOD
======================================================================

Never judge strategies only on one backtest.

Use time-series/walk-forward evaluation:
- train/tune only on past data;
- test on future slices;
- use realistic intraday timestamps matching decision/execution logic;
- include transaction fees;
- model data latency/conservative execution assumptions;
- measure M1/M2/M3/M4 analogues;
- assess stability across bull, bear, high-volatility, low-volatility, trending and mean-reverting periods.

Maintain an experiment table:
Experiment ID
Hypothesis
Data window
Features
Model
Portfolio rule
Cost assumptions
Cumulative return
Sharpe
Max drawdown
Turnover
Notes
Keep/Reject decision

Always compare to simple baselines. A complex model must beat them robustly, not just in-sample.

Potential ensemble philosophy:
- medium-horizon momentum provides trend capture;
- short-horizon reversal can reduce chasing;
- volatility scaling prevents single-name risk domination;
- sector-relative ranking reduces broad market beta;
- cash/risk-off regime protects drawdown;
- turnover penalty prevents score destruction through fees;
- optional public-news layer should be small and only retained if incremental.

11. WHAT "WINNING-ORIENTED" MEANS FOR THIS USER
======================================================================

The user is a complete coding/quant beginner but is willing to use AI intensively. Therefore:
- AI should write/review most boilerplate and code.
- The user should still understand each module's purpose, inputs, outputs and failure modes.
- Every critical path must have tests and observable logs.
- Complexity should be earned via measured incremental value.
- Reliability and scoring-aware risk control are competitive advantages.
- The project should first become VALID + REPRODUCIBLE, then COMPETITIVE, then SOPHISTICATED.

Preferred development sequence:
Stage 0: account + repo + Python + starter-kit setup.
Stage 1: register and verify API/credentials without exposing secrets.
Stage 2: build a completely valid rule-based baseline and local evaluator.
Stage 3: build historical data pipeline and backtest harness.
Stage 4: develop multiple transparent alpha baselines.
Stage 5: add portfolio optimizer, turnover control and regime/risk layer.
Stage 6: run walk-forward comparisons and ablations.
Stage 7: optionally test ML and LLM news overlay.
Stage 8: harden automation, logging, fallback and VPS deployment.
Stage 9: rehearse end-to-end in Validation.
Stage 10: freeze a robust Official version and operate conservatively.
Stage 11: prepare reproducible final materials/disclosures.

The correct mindset is not "use the fanciest model." It is:
"Build the most reliable system that extracts repeatable edge under the actual scoring formula and rules."
